# SSH Brute-Force Log Analyzer with Automated Alerting

A small Python project that simulates SSH authentication logs, detects brute-force
patterns by counting failed logins per source IP, and writes a JSON alert file that a
dashboard can consume.

All data is **simulated**. The log is generated by a script and the attacker IPs come
from ranges reserved for documentation (RFC 5737). No real systems or people are involved.

## Features

- Generates a realistic `auth.log` with random IPs and `Failed` / `Accepted` password events.
- Filters `Failed password` entries with the `re` module (handles `invalid user` variants).
- Aggregates failures per IP with a dictionary.
- **Flags any IP that exceeds a configurable threshold (default: 5 failed attempts) as a
  "Potential Brute Force Attack".**
- **Writes `alerts.json` containing the timestamp, source IP and alert level for each alert.**
- Prints a readable console report.

## Requirements

- Python 3.8 or newer
- No third-party packages (standard library only)

## How to run

Run the generator first, then the analyzer.

```bash
python3 generate_auth_log.py
python3 analyze_auth_log.py
```

On Windows, use `python` or `py` instead of `python3`.

### Command-line options

```bash
python3 analyze_auth_log.py [log_file] [-t THRESHOLD] [-o OUTPUT]
```

| Option | Default | Meaning |
|---|---|---|
| `log_file` | `auth.log` | Log file to analyze |
| `-t`, `--threshold` | `5` | Alert when an IP's failures **exceed** this number |
| `-o`, `--output` | `alerts.json` | Where to write the alert file |

## How to adjust the threshold for different security policies

The threshold is the number of failed attempts an IP may make before it is flagged.
An IP is flagged when its failures are **greater than** the threshold
(with the default of 5, an IP with 5 failures is not flagged and an IP with 6 is).

There are two ways to change it.

**Option 1: at run time (no code changes).**

```bash
python3 analyze_auth_log.py auth.log --threshold 10
```

**Option 2: change the default in the script.** Open `analyze_auth_log.py` and edit the
constant near the top:

```python
THRESHOLD = 5   # change this number
```

Suggested starting points (tune them to your environment):

| Policy | Threshold | When to use |
|---|---|---|
| Strict / high security | 3 | Internet-facing servers, admin or privileged accounts |
| Default | 5 | General-purpose servers (the value used for this task) |
| Relaxed | 10 to 20 | Environments where users often mistype passwords, or to reduce alert noise |

Notes:
- A lower threshold catches attackers sooner but produces more false positives from
  users who simply forgot a password. A higher threshold is quieter but slower to react.
- Alert levels scale with the threshold, so they stay meaningful when you change it.
- To flag IPs that *reach* the threshold instead of exceeding it, change `>` to `>=`
  in `build_alerts()` (`if s["count"] > threshold:`).
- The threshold must be 1 or higher.

### Alert levels

Based on how far the failure count is above the threshold (T):

| Level | Condition |
|---|---|
| MEDIUM | more than T failures |
| HIGH | 4 x T or more |
| CRITICAL | 10 x T or more |

With the default T = 5: MEDIUM is 6 to 19, HIGH is 20 to 49, CRITICAL is 50 or more.

## Output: `alerts.json`

Example (shortened to one alert):

```json
{
  "generated_at": "2026-11-17T10:08:52Z",
  "source_log": "auth.log",
  "threshold": 5,
  "total_failed_attempts": 378,
  "unique_ips_with_failures": 106,
  "alert_count": 3,
  "alerts": [
    {
      "timestamp": "2026-11-17T10:08:52Z",
      "source_ip": "203.0.113.45",
      "alert_type": "Potential Brute Force Attack",
      "alert_level": "CRITICAL",
      "failed_attempts": 100,
      "threshold": 5,
      "unique_usernames_tried": 7,
      "usernames_tried": ["admin", "oracle", "pi", "postgres", "root", "test", "ubuntu"],
      "first_seen": "Nov 16 00:07:24",
      "last_seen": "Nov 16 08:40:15"
    }
  ]
}
```

| Field | Description |
|---|---|
| `timestamp` | When the alert was generated (ISO 8601, UTC) |
| `source_ip` | The offending IP address |
| `alert_type` | Always `Potential Brute Force Attack` |
| `alert_level` | `MEDIUM`, `HIGH` or `CRITICAL` |
| `failed_attempts` | Failed logins from this IP in the log |
| `threshold` | Threshold in effect when the alert was raised |
| `unique_usernames_tried` / `usernames_tried` | Distinct usernames the IP attempted |
| `first_seen` / `last_seen` | First and last failure as written in the log (syslog format has no year) |

If no IP exceeds the threshold, the file is still written with `"alert_count": 0` and an
empty `alerts` list, so a dashboard always has a valid file to read.

## How it works

1. **Parse**: `FAILED_RE` matches `Failed password for [invalid user] <user> from <ip> port <port>`.
   Named groups extract the fields, and `Accepted password` lines are skipped.
2. **Aggregate**: a dictionary maps each IP to its failure count, the set of usernames it
   tried, and the first and last time it was seen.
3. **Compare**: `build_alerts()` compares each IP's count with the threshold.
4. **Format and save**: flagged IPs are assembled into a JSON structure and written to
   `alerts.json` with `json.dump`.

## Testing the threshold

Create a log with exactly 5 and 6 failures and check which IP is flagged:

```bash
python3 - << 'PY'
lines = []
for ip, n in [("10.0.0.5", 5), ("10.0.0.6", 6)]:
    lines += [f"Nov 16 01:00:{i:02d} h sshd[1]: Failed password for root from {ip} port 22 ssh2" for i in range(n)]
open("test.log", "w").write("\n".join(lines) + "\n")
PY
python3 analyze_auth_log.py test.log -o test_alerts.json
```

Only `10.0.0.6` is flagged. Re-run with `-t 3` and both are flagged.

## Limitations

- The check is a plain count over the whole file. Real detection should also use a time
  window (for example, 10 failures within 60 seconds).
- Only `Failed password` events are inspected, not public-key failures or other sshd messages.
- The IP regex does not validate octet ranges, which is acceptable for system-generated logs.

## Possible improvements

- Time-window detection to catch fast bursts.
- Flag a successful login that follows many failures from the same IP (possible compromise).
- Generate a firewall block list from flagged IPs.
- Test against real sshd logs from a lab environment such as a Wazuh deployment.
